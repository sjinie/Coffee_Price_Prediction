## 1. 학부 캡스톤: Attention-LSTM으로 가격 수준 예측

- 시도: 거시경제·기후 데이터를 붙여 14일 뒤까지의 가격을 예측했다. VAR, LSTM, Entmax Attention을 붙인 LSTM을 비교했다.
- 결과: 가격 RMSE는 VAR 10.23, LSTM 6.70이었다. 숫자는 좋아 보였지만 비교할 기준선이 없었다.
- 나중에 찾은 문제: 테스트 입력을 스케일링하지 않았고 테스트 손실을 보며 학습률과 epoch를 조정했다. 방향 손실을 `sign()`으로 계산해 기울기가 0이었고 결측을 병합 전에 앞 값으로 채워 미래 정보가 섞였다. 80/20으로 한 번만 나눴다.
- 결정: 같은 문제를 기준선과 시간 순서 평가부터 다시 설계한다(노트북 01의 7절).
- 근거: `data_code/old_code/model_code/`, `docs/old_docs/*.pdf`, `docs/old_docs/README.md`

  1. 제목 규칙 점수: 2022년 학습 구간에 신호가 거의 없어 효과를 추정하지 못했다.

## 8. 첫 비교에서 모든 지평이 Naive였다

- 시도: 2015년부터 학습하고 한 번 나눈 검증 구간으로 비교했다.
- 결과: 세 지평 모두 현재가 유지(Naive)가 가장 좋았다. 60일 LightGBM은 RMSE가 8% 낮았지만 균형정확도가 0.49였다.
- 결정: Naive가 이기고 방향이 50% 근처라면 아무것도 예측하지 못한 것이다. 그래서 학습 설계를 바꿨다. 자료를 2005년부터 모으고 2006년부터 학습했다. 2012–2021년 연도별 walk-forward 10회로 고르고 2022–2025년은 보류 구간으로 남겼다. 원산지 통화(헤알·페소), 해상 운임, 이상기후 파생변수, ENSO, 해거리 주기를 추가했다. 수익률 회귀에 더해 상승 확률과 미래 변동성도 예측하기로 했다. 상승 확률은 확신이 없으면 판단을 보류한다.
- 근거: `f6851d9`, 계획 변경 기록

## 10. 무엇이 예측되고 무엇이 안 되는가

이 항목의 숫자는 평가 표본을 고치기 전(16 이전) 값이다. 고친 뒤의 값은 16에 있다. 결론은 바뀌지 않았다.

- 수익률(노트북 03): 모든 모델이 Naive보다 나빴다. 5일 LightGBM +0.9%가 가장 가까웠다. 단순 LSTM은 20일에서 +16.7%였다(고친 뒤 +17.1%). 학부 모델에서 Attention·정적 피처 분기·복합 손실을 뺀 모델이다.
- 후보 범위: 그래디언트 부스팅은 LightGBM 하나만 넣었고, 같은 계열인 XGBoost는 빼서 시험하지 않았다. DLinear는 closed form으로 단순화한 구현(피처·시점마다 계수를 두는 Ridge)이라, 시간 가중치를 피처끼리 공유하던 이전 DLinear(PyTorch)와 구조가 다르다. 이전 구조는 새 평가 방식으로 다시 돌려 보지 않았다.
- 방향(노트북 02·03): 가격 + 기후 피처의 LightGBM 분류기를 골랐다. 확률을 기본 비율 쪽으로 75–80% 줄이자 Brier가 기본 비율보다 조금 나아졌다. 보류 구간 AUC는 0.54 / 0.60 / 0.66이다. 신호대로 산 구매 단가는 정기 구매 대비 보류 구간 +0.83%로, 무작위(+0.93%)와 차이가 없었다.
- 변동성(노트북 04): HAR이 20일 RMSE를 개발 구간 13.2%, 보류 구간 18.5% 줄였다. 개발 구간의 13.2% 감소는 bootstrap 95% 구간이 0을 포함하지 않았다. 80% 범위 적중률은 보류 구간 76%(20일), 71%(60일)였다. 전체 기간을 기준으로 매긴 위험 등급은 고변동 국면에서 정보를 잃었다. 기준을 최근 3년 대비 백분위로 바꿨다.
- 결정: 서비스의 중심 전망은 현재가, 주 정보는 예상 범위와 위험 수준, 상승 확률은 확신할 때만 신호를 내는 보조 정보로 한다.
- 근거: `91f6594`, `56ddb16`, `ebc7b11`

## 11. 뉴스는 이미 일어난 일을 설명했다

- 시도: 노트북 05에서 미리 정한 규칙으로 진단했다. 5일 수익률(기준 = 현재가)에 뉴스 점수 계수 하나를 더해 2023–2025년 walk-forward로 평가하고 블록 bootstrap 구간이 0보다 작고 세 해 모두 좋아질 때만 채택하기로 했다.
- 결과: 2022–2025년 기사의 분석 지연은 중앙값 405–1,545일이었고 실시간으로 분석된 기사는 4건뿐이었다. 점수와 가장 강하게 관련된 것은 기사가 나온 날의 수익률(상관 0.21)이고 이후 수익률과의 상관은 모두 ±2 표준오차 안이었다. 실험은 ΔRMSE +0.0003 [−0.0001, +0.0006]으로 채택 규칙을 통과하지 못했다.

## 13. 서비스 다시 만들기

- DB: 예측 행은 덮어쓰지 않는다. 같은 기준일에 backfill이 있으면 live는 저장되지 않는다. 활성 모델은 부분 유일 인덱스로 하나만 허용한다. 일별 뉴스 점수 테이블은 `news_articles`에서 언제든 다시 계산할 수 있어 만들지 않았다.
- API 이미지: `db.py`가 pandas 없이 동작하게 해 API 이미지를 274MB로 줄였다. 파이프라인 이미지는 torch를 빼 2.78GB에서 1.05GB가 됐다.
- 뉴스 소스: 6의 403 차단에 더해 약관이 비상업 이용만 허용해서 Daily Coffee News를 뺐다. Yahoo KC=F 뉴스는 2026-10-03에 확인했을 때 0건이라 뺐다. Google News RSS 제목 형식과 해시를 보관 분석과 맞춰 같은 기사를 다시 분류하지 않는다. 실제 실행 한 번에 10건을 분류했고 비용은 0.000144 USD였다.
- 검증: 임시 PostgreSQL 17.11로 pytest 37개, 실제 backfill·daily 실행, 컨테이너 안 migrate·backfill, 브라우저 확인(데스크톱·375px, 밝은·어두운 화면)을 했다. VM과 GitHub Actions 실제 실행은 운영 전환 때 한다.
- 의존성 확인(2026-10-03): GitHub Actions는 기존 SHA(checkout v5.1.0, setup-python v6.3.0, setup-node v5.0.0)가 공식 태그와 일치하고 모두 node24 런타임이라 유지했다. 최신 major(v7)로 올릴 이유가 없었다. 프론트는 기존 고정 버전(vue 3.5.43, vite 8.3.0, @vitejs/plugin-vue 6.0.8)을 유지했다. 패치(vite 8.3.2)가 있지만 `npm audit`이 0건이다. 기반 이미지는 digest로 고정했다(python 3.12.15, node 22.23.3, nginx 1.30.5, postgres 17.11, caddy 2.11.4).
- 근거: `99b76d5`, `4ebf569`, `d378739`

## 14. 독립 리뷰 반영

- 시도: 읽기 전용 리뷰어가 서비스 코드와 배포 스크립트를 따로 검토했다.
- 반영한 것:
  - (HIGH) 장중에 수동 실행하면 끝나지 않은 오늘 봉으로 예측이 저장되고 덮어쓰지 않는 규칙 때문에 고칠 수 없었다. 이제 23:00 UTC 마감이 지난 거래일의 가격만 쓴다.
  - SSH 터널을 2초 기다리는 것으로만 확인했다. 포트가 열릴 때까지 최대 30초 기다리고 DB 연결 시간 제한을 10초로 뒀다.
  - FRED·AI Gateway 키가 없으면 예측 전에 멈췄다. 경고로 바꿔 가격 예측은 저장한다.
  - 테스트를 추가했다. 목표일이 정확히 일치하는지, 뉴스 예산과 건수 상한, 뉴스가 실패할 때 예측을 유지하는지(종료 코드 3), 실패를 기록하는지(종료 코드 1)를 검사한다.
  - 화면: API 하나가 실패해도 예측 화면은 남게 했다. 뉴스 날짜를 뉴욕 기준으로 통일하고 소급 계산을 표시했다. 접근성 마크업과 nginx의 API 주소 재조회도 고쳤다.

- 근거: 이전 운영의 06:17 UTC 예약 실행은 실제로 11:47–14:08 UTC에 시작됐다(최근 6회). 첫 실시간 예측이 나오는 시각은 이 지연을 감안해서 본다.
- 리뷰 반영: 처음 고친 백업 검증 명령(`pg_restore -l | head`)도 같은 이유로 실패를 가렸다(PR #8 Codex 리뷰). 목록을 변수에 먼저 받도록 고쳤고, 깨진 dump 파일로 이전 명령은 exit 0, 고친 명령은 exit 1임을 확인했다.
- VM 확인 반영: 배포 폴더가 git 저장소가 아니고 root 전용이라 `git pull`과 `cd`가 실패하는 명령이었다. 이전 운영처럼 `git archive`로 보내 해시를 대조하고, 이전 폴더는 지우지 않고 백업으로 옮기도록 바꿨다. backfill 뒤의 `unset`이 종료 코드를 0으로 덮는 문제(PR 리뷰)는 `rc`에 먼저 저장해 고쳤다. zsh에서는 `status`가 읽기 전용 변수라 쓸 수 없다. 교체·되돌리기 명령은 Debian 컨테이너에 같은 경로를 만들어 실행해 확인했다.
- 재시도 반영(PR 리뷰): 같은 날짜로 절차를 다시 실행하면 `cp`가 원본 `.env` 백업을 새 설정으로 덮어, 되돌릴 때 이전 app에 새 `.env`가 돌아왔다. 백업을 실행마다 새로 만드는 폴더 하나에 모으고 `mkdir`로 먼저 만들게 했다. 폴더가 이미 있으면 백업 전에 멈춘다. 같은 컨테이너에서 백업 재시도는 멈추고 원본이 유지되며, 되돌린 뒤 원본 `.env`가 돌아오는 것을 확인했다.


## 20. 산지 기상 주간 API (2026-10-04)

- 결정: 화면용 `weather` 표와 `/api/weather`를 추가했다. 기존 모델 입력과 공개 지연 규칙은 유지한다. 가격과 시작 기간을 맞춰 `collect_start`(2005-01-01)부터 적재하고 `daily`는 실행일(UTC) 포함 최근 30일을 갱신한다.
- 주 정의: 연 시계에서 같은 시기가 같은 각도에 오도록 ISO 주 대신 1월 1일 기준 52주를 쓴다. 마지막 주 8–9일도 합계와 `days`를 그대로 보내 프론트에서 강수를 7일로 환산한다. 결측을 채우지 않고 지표별 NULL을 집계에서 제외한다.
- 응답: 압축을 추가하지 않고 연도 × 52칸 배열로 줄였다. 2005-01-01–2026-10-04 합성 자료 47,682행(6산지)으로 실제 API 컨테이너를 호출했을 때 산지별 응답은 압축 없이 24,447–24,454바이트였다. 실제 관측값의 응답 크기는 별도 확인 대상이다.
- 독립 명령: 기상을 처음 채울 때 `backfill`로 오래된 로컬 가격까지 운영 DB에 덮어쓰지 않도록 `weather` 명령을 분리했다. 수집·모델·뉴스 실행 없이 보관 자료를 읽고 기상만 적재한다.
- 적재 근거: 선언·설치 버전 모두 psycopg 3.3.6이다. [해당 태그의 공식 문서](https://github.com/psycopg/psycopg/blob/3.3.6/docs/api/cursors.rst)에서 `executemany(returning=False)`의 `rowcount`가 영향받은 행 수의 합계임을 확인했다. 실제 PostgreSQL에서 신규·갱신·빈 배치 건수를 검사했다. 의존성 변경은 없다.
- 검증: 신규 테스트 10개의 실패를 확인한 뒤 구현했다. 외부 Python 3.12.15와 독립 PostgreSQL 17.11 컨테이너에서 전체 pytest 58 passed(기존 TestClient 관련 deprecation 경고 2건), API 이미지 빌드 성공. 소유자 생성 표에 default privileges가 적용되어 API 계정의 SELECT는 성공하고 INSERT는 거부됨을 확인했다. pandas·torch 없는 이미지에서 6산지 HTTP 200 및 잘못된 id 422를 확인했고 자체 소스 검토를 마쳤다. NASA 실호출·실제 데이터 전체 적재·VM 배포는 실행하지 않았다.
